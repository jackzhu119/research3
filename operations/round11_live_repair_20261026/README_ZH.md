# R11在线运维恢复：控制器内存与论文二进制上传

本修复针对2026-10-26学校R11已经运行的固定计划。它使用独立管理进程，在内存中修补原运维模块；不改原科学代码、签名计划、参数、模型、checkpoint、result/completion收据，不取消或停止任何科学Slurm作业，也不重置任务计数。

## 两个已定位的问题

1. 控制器读取`tasks.json`时使用`read(64MiB+1)`。即使文件较小，这个长度参数也可能请求大块预分配，实际日志在该调用触发`MemoryError`。修复使用文件实际大小及小块读取，保持原JSON大小上限和无效输入语义；不把坏任务历史当成空队列重建。
2. `operator_train_task`将模型NPZ列为论文工件，而原论文传输器只接受UTF-8文本。真实算子NPZ已复现`ValidationError/source_utf8_invalid`。修复在通道A以明确命名的严格base64 ASCII表示传输二进制，记录原路径/字节/SHA、表示文件字节/SHA、严格解码还原说明。原NPZ保持原样，通道B完整原始归档继续独立运行。文本CSV/JSON保持原字节，不删行、不重算科研指标。

原日志及固定身份见`INCIDENT.json`；可复现证据与发布前测试见`proof/`。错误原因仅记录经过白名单约束的固定错误码，不打印凭据、HTTP响应体或任意异常文本。

## 实际恢复行为

- 默认安装/检查不申请GPU、不提交作业、不发信号。
- 显式恢复只接管已退出的控制器；原控制器仍持锁则保留。
- 第一轮Slurm观察仅核对现有4个槽位及作业，不提交；只有显式`--submit`重申后才允许原调度策略对真实结束的allocation补位。已运行或排队的原作业不会重复提交。
- 替换论文上传时只允许向同UID、精确原入口/子命令/原计划身份匹配的论文上传进程发送SIGTERM；PID启动身份会复核。不向科学worker、full归档、reporter、monitor或未知进程发送信号。
- 原有效上传缓存与远端回执保留，错误二进制捕获由新表示精确恢复；不会通过放松SHA检查消除错误。
- 管理进程在后台运行，启动回执区分实际就绪、仍在启动和已退出。启动成功不代表所有远端文件已经上传，也不等于四张GPU均已分配。

原4个作业为775286、775287、775288、775289，对应64G/16CPU/1GPU；恢复时以实际Slurm观察为准。最后一次故障前回传完成58/10270，训练仍在前进，这些数据和检查点都保留。
