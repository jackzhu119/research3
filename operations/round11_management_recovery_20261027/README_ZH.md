# R11 管理、报告与回传恢复

本修复只作用于现有R11的管理进程及独立旁路进程，保留当前四个计算作业、原始计划、全部任务尝试记录、科学结果和断点。不会新建实验、修改方法参数、重训已完成任务或取消R1/R11/M12作业。

## 已确认的问题

- 学校日志确认：北京时间11:08:51，旧控制器读取`runtime/tasks.json`失败，被旧读函数转为`None`，再由`_state()`抛出`ValueError`。该异常未被旧控制循环的`OSError`重试分支接住，因此控制器退出。底层文件系统为什么发生这一次读取失败尚无直接证据，不能宣称任务文件永久损坏。
- 完整归档并未停住：在11:13网络错误之后，仍连续成功上传和GET校验，学校日志最后记录到12:56:49。旧完整上传器只在整批任务结束后更新通道状态，因此先前的`RETRYING`长期滞留，不能代表当前上传状态。
- 报告状态停留在591项，最新计算已达900项。代码复核发现报告器把完成任务读取放在异常保护之外，短暂读失败也可能让报告器退出；修复整个观察与报告循环，而不把旧时间戳冒充最新成功。
- 另检查到调度器独立读取状态文件时也可能把短暂缺失误作新状态；部分网络层具有内部无限重试，外层无法及时更新状态。这些路径一并测试和处理。

## 修复行为

1. 对现有任务状态、四槽位调度状态和提交回执进行实际大小读取与有界重试。读不到就显示`OBSERVATION_RETRY`，保留全部历史并禁止依据未知状态补提；不会创建空任务表或空调度历史。
2. 控制器先完成一次真实队列观察及任务状态观察才签发READY；之后持续更新观察时间。只能按原授权补齐原有四槽位，资源仍为每槽1GPU、16CPU、64G。
3. 报告器独立运行，使用隐藏CUDA的CPU子进程生成原生报告；状态区分观察到的计算覆盖、实际报告覆盖、最近成功时间和当前错误，失败后重试。
4. 正在工作的论文数据/完整归档上传器保留。新增旁路观察器读取现有缓存和有界日志尾部，分别记录活性、最近上传事件及已有校验证据；观察心跳不代表文件已上传。原上传器自然释放锁后，新上传器才接管，沿用原分组和分片缓存。
5. 后续网络请求的重试可退出、状态持续刷新；保留TLS验证、二进制无损表示、完整远端GET与SHA校验。网络或报告失败均不停止科学计算。
6. 管理进程接管核对同用户、脚本身份、准确计划、PID和启动时钟。只允许向已确认的管理进程发送温和退出请求；科学进程和其他轮次不在匹配范围内。重复执行复用已启动进程。

## 执行与检查

独立入口为`delivery/REPAIR-PAPER3-R11-MANAGEMENT.py`。默认仅安装；用户显式使用`--apply --submit`才应用现有R11管理修复。使用既有`SUBMIT_AUTHORIZATION.json`与提交历史，原计划身份不得变化。

默认管理目录为`$HOME/paper3-r11-management-recovery/work/97e4cadb17278532`。各角色分别有进程、READY、状态、心跳及日志文件。READY只说明锁和管理观察满足接管条件；归档完成仍需要原始科学文件清单与远端校验证据。

科学输入或已完成结果真正损坏时会明确报错并保留现场，不通过跳过校验或写入虚假COMPLETE来“恢复”。修复包不承诺消除学校文件系统、网络或GPU硬件的所有未来故障。实际学校恢复情况须在执行后根据新回执与新回传确认。
