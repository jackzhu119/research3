## 结论

第四至九轮的扩展软件检查未复现新的计算阻塞错误。学校第五轮已出现连续优化更新，第八轮已有成功完成任务，这些是运行证据；本目录的软件测试结果只用于验证程序路径，不能作为论文性能数据。

另发现并修复第一轮及恢复流程的三处后续问题：

1. **第一轮派生进程丢失兼容修复。** Python `spawn` 不继承父进程内存中的函数替换。原普通阶段和源扩展阶段子进程会重新落回旧显卡判断。新增引导调用当前第一轮实际安装包的同一运行桥接，在子进程导入原阶段代码前重新加载已验证的兼容规则。
2. **第一轮源扩展的跨节点身份不一致。** 扩展任务保留原始任务身份，源模型准备函数却重新使用当前节点标识构造身份。节点变化后可能在历史派发检查或最终回执检查时中断。运行时修正仅统一任务身份中的运行标识，实际执行设备和计时仍使用实际节点信息，并通过既有迁移校验和记录。
3. **旧在线安装器拒绝已修复入口。** 旧安装器校验固定文件 SHA，授权修复后重新执行旧下载安装命令会失败。新增 `resume_existing.py` 读取已经存在的计划和启动配置，直接恢复原持久控制器，不重新安装或重建计划。已验证第五、六、八、九轮；存活组件直接复用，第九轮同时保留两条上传通道。

成功标志：`FUTURE_PATH_REPAIR_INSTALLED`。第一轮后续子进程会输出 `R1_OWNED_CHILD_RUNTIME_BOOTSTRAPPED`。普通阶段与源扩展阶段均保留原进程入口名称、参数和 IPC 所有权协议。

安装记录位于 `$HOME/paper3-runtime-fixes/future-path-v2/APPLIED.json`。

如果第五、六、八或九轮今后确实需要手动恢复，使用已缓存的新程序并指定轮次，例如：


当前正常运行或排队的任务无需执行恢复操作。第六轮恢复沿用其现有 `hpc_gpu1` 设置；第一轮、第四轮的调度仍使用各自原生机制。
