# Round 5 single-allocation runtime

Round 5 requests one ordinary Slurm job on one node of `hpc_gpu`, with three GPUs. Default resource flags are `--nodes=1 --ntasks=1 --cpus-per-task=36 --mem=128G --gres=gpu:3`. The CLI `--cpus 12` is a per-GPU-slot CPU budget; `--memory-total 128G` is the authoritative shared host-memory pool for the entire job and is never multiplied by the number of GPUs. An equal-share display budget is 128/3 GiB per slot, not a process memory limit. No 42G/43G rounding or virtual-address-space limit is applied. The earlier per-slot `--memory` flag is not accepted as an abbreviation of the new flag.

Three child workers run within that single allocation. Each sees one allocated CUDA token as its own `cuda:0` and a disjoint 12-CPU affinity group. The scheduler uses only the GPU mapping supplied by the allocation and never enumerates the node to claim other GPUs. If the observed CPU mask contains fewer cores than requested, the public observation records the smaller actual sets and logs the shortfall rather than pretending the requested allocation was observed. `hpc_gpu` is a partition, not an invented physical node name; there is no queue fallback or additional `srun` dependency.

`START.py` prepares the numerical plan using the standard library and the existing interpreter. It does not run full tests, pilot training, whole-tree data scans, or package installation at school startup. Passing `--submit` starts the independent GitHub monitor and then the detached allocation controller. Preparation/PIDs acknowledge local startup; a durable Slurm job ID acknowledges scheduler acceptance; actual worker steps/session counters establish scientific computation.

The outer controller owns only its exact `paper3r5-<hash>` marker and durable attempt names. It fsyncs each submission intent before `sbatch`, then reconciles `squeue` and `sacct` to adopt lost acknowledgements without duplicate jobs. QoS rejections wait with capped backoff rather than submitting arrays. Socket uncertainty reserves the sole allocation until queue/accounting evidence resolves it. Observation failures pause new submissions while an existing allocation keeps working.

The within-node scheduler dynamically launches ready task dependencies into at most three slots. A completed task frees its slot for another ready task. A scientific task failure records its error and leaves independent siblings running; dependencies on missing results remain waiting. COMPLETE results are reused, unfinished numerical fits read their own checkpoint, and session-level evaluations reuse completed rows. Explicit FAILED results are not silently erased to manufacture success.

Batch stdout begins with the job/node identity. Every 30 seconds `ALLOCATION_PROGRESS` reports the three slot tasks, actual worker step/session counters and their ages. Whole-job logs are `logs/train-%j.out/.err`; each task attempt has separate `logs/task-INDEX-attemptN.out/.err`. A pending job is reported as queued with its reason, never as neural training merely because its submission was accepted.

USR1 signals reach the allocation scheduler and its children as checkpoint requests. Exit 75 and terminal Slurm timeouts/preemptions allow a new single allocation after accounting reconciliation, preserving completed work. Explicit cancellation, TERM termination receipts and STOP markers remain stopped. There is no cumulative twelve-hour budget; a single allocation still has the school's configurable Slurm time limit (default `5-03:00:00`). No action cancels, edits or overwrites prior-round jobs or outputs.

The public package is isolated under `~/paper3-round5/<payloadhash>/`, and imports target `paper3r5` plus vendored frozen kernels. Source-only installation uses `flock` and a standard same-filesystem rename compatible with Linux 3.10. Isolated `-I -S -B -u` Python startup adds explicit package/project/venv paths without running `.pth` startup hooks. No new packages or Slurm GPU-binding features are required.

GitHub synchronization independently retries failures and does not control training. Core status is `paper3-r5-progress:monitoring/paper3-round5/status.json`; the optional external phase writes `weibo-status.json`. Existing R2/R3/R4/R5 private credential files are discovered by path and read without changing them. Raw predictions, participant arrays and credentials are excluded from public status. The displayed requested resource budgets remain distinct from observed CPU/GPU use.

`RUNBOOK_ZH.md` records operational commands. `VALIDATION.json` will record the combined exact-version CPU tests and their limits. Mock Slurm, real CPU child processes, Bash 4.2 signals and isolated-installation checks are software evidence, not a school GPU execution or accuracy claim.
